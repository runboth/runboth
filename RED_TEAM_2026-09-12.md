# Red team, 2026-09-12

Eight public repositories the project had never been tuned against, plus a corpus written
specifically to make the tool lie. The goal was to find reasons not to ship it.

Repos used, chosen for variety of layout and idiom rather than convenience: **sqlparse** (parser,
stateful classes), **more-itertools** (5,630-line module, generator-heavy), **cachetools**
(method-heavy), **packaging** (src/ layout), **boltons** (large, flat, zero deps), **arrow**
(datetime, the worst case for a differential tester), **pluggy** (src/ layout, hook machinery),
**tenacity** (async-heavy, and its functions genuinely sleep).

The eight previously-measured repos (attrs, click, flask, httpx, jinja, markupsafe, requests,
toolz) were deliberately excluded, because a tool measured on the repos its bugs were fixed
against is measuring itself.

## Method

`scripts/redteam.py` runs real historical commits through `adjudicate` and applies an automated
false-positive oracle:

> For every function reported as `changed`, compare that function's own source at base and at
> head. If the source is identical, the verdict is only legitimate when something it calls
> changed, or its own constructor changed. Anything else is a probable lie.

That oracle is the automated version of how the measurement-path defect was caught by hand
earlier the same day.

## What held up

**Zero false positives.** Across **2,548 adjudicated functions** on eight repositories, the oracle
flagged exactly one: `__dir__` in `packaging/tags.py`. Verified by hand, it is a **true** positive
and the best single demonstration the project has. Its own source never changed a character. The
commit added a new public name to the module, so the function now returns a different list. A
function nobody touched, caught by executing it rather than reading a diff.

On the purpose-built adversarial corpus of 22 functions
(addresses in default `repr`, `datetime.now`, unseeded `random`, `uuid4`, `os.getpid`, set
iteration order, mutable default arguments, module-level accumulators, generators, `__file__`
paths, paths inside exception messages), **not one was reported as changed**. Two controls in that
corpus that had to come back `no_change` did.

**Nondeterminism is caught, not reported.** `uuid4` and `os.getpid` abstained with "before version
differs from itself across processes". This is the cross-process determinism gate doing exactly
its job.

**Correct scoping.** A commit touching one file produced two records, not a whole-repo sweep.

**Real security fixes handled sensibly.** On sqlparse's ReDoS fix (`d1d8060274`) it adjudicated 22
functions with zero abstentions, identified the two genuinely new helpers, and confirmed the other
15 were behaviour-preserving. For a performance fix that is the correct and useful answer.

**No dependencies, no network, no model.** Verified: the shipped path imports `adjudicate`,
`blast` and the standard library. `pyproject.toml` declares no dependencies. There is no z3.

## Bugs found, and fixed

### 1. The worker cap existed on one path and not the other (high)

`precommit.py` capped its thread pool at 4 workers with `RUNBOTH_WORKERS`, a fix made after
measuring that unbounded parallelism made things slower. `adjudicate.py`, which is the path the
GitHub Action and the pull-request report use, still used raw `cpu_count()`. Each job spawns three
interpreters, so on a 20-core machine that is sixty processes competing.

The effect was that verdicts depended on how busy the machine was. Same repository, same commits,
same budget, same 230 functions:

| Condition | Abstention rate | Median s/commit |
|---|---|---|
| Loaded, uncapped (as shipped) | 37.8% | 61.6 |
| Idle, uncapped | 7.8% | 11.4 |
| **Loaded, capped at 4** | **0.9%** | **14.3** |

Every one of those extra abstentions was the 30-second wall clock, which under contention
measures the machine rather than the code. This mattered more than it looks: a GitHub runner is
two shared cores, so the Action would have shipped behaving like the worst row.

### 2. Tests and benchmarks reported as findings (medium-high)

Helper functions inside `benchmarks/` and `tests/` were adjudicated and reported alongside library
findings. On sqlparse's ReDoS commit, five of seven findings were helpers in
`benchmarks/bench_dollar_quote_redos.py`, a file whose entire purpose is to be rewritten next to
the fix.

Worse, it was also the cause of the tool's worst failure mode. Three of eight more-itertools
commits **timed out at 700 seconds and returned nothing at all**. All three touched only
`tests/test_more.py`. After filtering, all three return in **0 seconds** with a named reason:

```
no library Python files changed; tests/test_more.py is tests, benchmarks or docs
(set RUNBOTH_ALL_PATHS=1 to include them)
```

Silence never covers the skipped files: they are named. `RUNBOTH_ALL_PATHS=1` restores the old
behaviour for coverage studies.

### 3. Constructor changes amplify into dozens of findings (high), FIXED

cachetools `dd181c5a72` adds validation rejecting a negative `maxsize`. It is a two-line change to
`Cache.__init__`. RunBoth reports **45 functions changed**, of which **39 have an "after" side that
is nothing but a failed construction**:

```
FIFOCache.clear    args: FIFOCache(-2) .clear()
  used to:  return None
  now:      fail to construct (ValueError)
```

`FIFOCache.clear` did not change. What changed is that you can no longer build a `FIFOCache(-2)`.
Every statement is individually true and the verdict is not a false positive, but attributing the
change to `clear` is a category error, and a user's first pull request showing 45 findings for one
intended line is a user who turns the tool off.

Fixed at the report level, not the engine level, by `adjudicate.collapse_constructor_findings`,
used by both the pull-request report and the commit gate so the two cannot drift. Findings whose
"after" is a failed construction fold into the constructor that caused them. **45 findings became
8**, one per class, and nothing is dropped: a folded finding with no constructor to hang it on
stays, because a disappearing finding is the one outcome this tool must never produce.

### 4. Every method finding was printed wrong (high), FIXED

Found while checking the fix above. A method witness carries the construction and the call as two
pieces meant to be concatenated, `["FIFOCache(-2)", ".clear()"]`. All four report sites
comma-joined them and wrapped the result in the function name again:

```
FIFOCache.clear(FIFOCache(-2), .clear())      before
FIFOCache(-2).clear()                          after
```

This affected **every method finding the tool has ever printed**, which is the most convincing
part of the product. Constructors were worse still, printing `Cache(-2).__init__(-6, 2)`, which is
not how anyone builds a `Cache`. They now render as the construction they are, and the vague
`eff`-channel wording is replaced with what actually happened:

```
Cache(-6, 2)
  used to:  construct successfully
  now:      fail to construct (ValueError)
```

### 5. Build and task-runner files drowned a repo in abstentions (high), FIXED

pypa/packaging abstained on **42.6%** of functions. 51 of the 55 abstentions were one reason:
`No module named 'nox'`. `noxfile.py` holds 17 functions and appeared in three of six sampled
commits, so half the sample produced nothing but abstentions about a task runner.

These files are in a large fraction of Python repositories and every one of them imports dev-only
dependencies the adjudicating environment does not have. `noxfile.py`, `setup.py`, `tasks.py`,
`fabfile.py`, `manage.py`, `dodo.py` and friends are now treated as non-product, like tests.

The skip list was also **tightened** in the same pass: `scripts/` and `fixtures/` were in it and
were removed before shipping, because plenty of projects keep real product code under `scripts/`.
Skipping real code is a worse failure than reporting noise.

### 6. Added and removed functions vanished from the report (medium), FIXED

When a commit produced no witnessed behaviour change, the "no behaviour change found" branch
reported cosmetic differences, abstentions and skipped files, but never structural ones. On
sqlparse's ReDoS fix, which adds two helpers, the entire report was "no behaviour change found"
with no mention that two functions had appeared. True, and it omitted the most obvious fact about
the commit.

Silence also no longer covers a skipped file. When filtering removes a changed file, the report
names it, the same rule the gate already applied to languages it cannot read:

```
RunBoth: no behaviour change found. Executed 15 function(s) in both versions at 40 inputs each.

2 function(s) were added or removed (find_delimited_spans, resolve_paired_delimiters); there is
no before-version to compare them against.
1 changed file was NOT checked because it is a test, benchmark or doc
(benchmarks/bench_dollar_quote_redos.py); nothing above refers to it
```

## Bugs found, NOT yet fixed

### 7. Latency on large modules (medium)

more-itertools at budget 40 runs 174 to 192 seconds per commit on a 5,630-line module, 193
functions per sweep. Fine for a pull-request bot, too slow for a commit gate on that repo. The
worker cap will have improved this; it has not been re-measured at that scale.

### 8. Dead weight in the wheel (low)

About 2,400 lines of formal-methods machinery from earlier generations ship in the package.
Nothing on the product path imports any of it: the gate imports `adjudicate`, `blast` and the
standard library, and that is all.

Removing it is a bigger job than it first looked, and the first version of this note got it wrong.
Only `smtval.py`, `kinduct.py` and `specgen.py` are genuinely orphaned. `hoare.py` is imported by
twelve other modules and `refine.py` by six, so what exists is an interconnected research subtree
hanging off the side of the package, not four files that can be deleted. It costs wheel size and
reviewer confusion, nothing else.

Two rows are worth reading closely rather than skimming. **arrow** is a datetime library, which is
the worst case a differential tester can be handed, and it produced no false positives across 283
functions. **tenacity** is the honest other end: a retry library whose functions genuinely sleep,
so checking it is slow and it abstains more than anything else measured. Neither number was
dropped for being inconvenient.

`packaging` fell from 129 functions to 78 once build-file filtering landed, because half its
sampled commits touched nothing but `noxfile.py`.

## Honest note on method

The first sqlparse run reported 37.8% abstention and a 61.6s median. Both numbers were measured
while two other red-team jobs held the machine. That is the third time in this project that a
contaminated benchmark nearly became a reported finding. The contamination was real here in a
useful way: it exposed bug 1. But the rule stands, and it earned its place in CLAUDE.md. Measure
the instrument before quoting the number.
